# Design

## 課題

ACC-01 は Nagi からの移動に SSO チケットと DID ヒントの両方を使うと定めていた。Nagi Space は本人の PDS 経由の API を呼ぶので、チケットだけのセッションは作れず（nagi-space-initial の design.md D2）、チケットは OAuth の `login_hint` に渡す DID を確かめるだけだった。利用者の手間は減らず、外部の設定と保存するデータだけが増える。

## 判断

### D1. 姉妹アプリの連携の規則

DID ヒントはすべての姉妹アプリに付け、チケットは「チケットだけでサインインが完結するアプリ」にだけ使う。Nagi Space は本人の OAuth 認可が要るので、DID ヒントだけを使う。botたんのお部屋は DID だけで動くので、チケットで承認画面を省ける。規則は同じで、アプリの事情によって使い方が分かれる。

- 代替案：Nagi Space もチケットを受ける（今の実装）。DID が本物かを確かめられるが、偽のヒントの害は「他人のハンドルで認可画面が開く」だけで、認証は認可サーバーが行う。AppView の設定、受け口のパスの切り替え、使用済みチケットの記録に見合わない。

### D2. DID ヒントの受け方

- `/login?did=` に加え、共有 URL（`/s/<id>?did=`）とトップ（`/?did=`）でも受ける。Nagi に貼られるのは共有 URL なので、`/login` だけで受けると ACC-01 を満たせない。
- 未ログインでヒントの形が正しいときだけ、サーバーで `/login?did=…&returnTo=<元のパス>` へリダイレクトし、`/login` が認可を始める。戻り先からは `did` を落とす。アドレスバーに他人の DID が残ったまま URL を共有されないようにするため。
- ログイン済みならヒントは使わない。
- 認可の開始に失敗したら、`did` の無い `/login` のハンドル入力に落ちる。認可サーバーで断られたら `/login?error=callback` に戻る。どちらも `did` が URL に残らないので、同じヒントで繰り返し認可へ進むことはない（お部屋がブラウザ側で持つ「試行済み」の印は要らない）。

## 失敗時の扱い

D2 のとおり。ヒントが壊れていれば無視し、通常のページを表示する。

## 個人情報の境界

DID ヒントは閲覧者本人の DID（公開の識別子）で、保存しない。使用済みチケットの記録（自宅DB、チケットの有効期限まで）は無くなる。

## 外部サービスの上限と費用

変化なし。AppView への設定追加が不要になる。
